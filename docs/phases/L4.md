# Phase L4 — Delivery to Claru, review, the 72-hour alert

What it adds (claru-integration.md, "How a delivery works", steps 2–6):

- **Automatic delivery.** A recording goes to Claru by itself once it is checked, cut and declared — no extra
  button, as decided. Each clip is one submission, sent in order:
  1. **Create** with the clip's declaration (category, country, site, device, mount from the declaration;
     `collectorId` = the uploader; `recordedAt` = recording start + the clip's start; `durationSeconds`
     measured from the clip) and the clip's `externalRef` (`cvu-<recording>-c01`, …).
  2. **Upload** the way Claru says: one PUT with every header it gives, or 64 MiB multipart slices (3 at a time).
  3. **Complete** each part (with the ETags for multipart).
  4. **Seal**. Accepted → "processing"; refused → the code and Claru's remedy are shown.
- **Safe to repeat.** The externalRef is the idempotency key: a stopped server, a dropped connection or Claru
  being down resumes the same submission; it never makes a second one. Delivery is retried for hours.
- **Claru's rules for waiting**: 429 and 503 (SEAL_TIMEOUT) wait exactly the `Retry-After` Claru sends.
- **Verdicts by polling** every 3 minutes (`CLARU_POLL_MINUTES`): processing → in review → approved / rejected.
- **Refused ≠ rejected.** Refused (at the door; nothing created): fix it, "Retry delivery" under the SAME
  reference — the declaration can be changed first. Rejected (a clip exists): "Send again as a new
  submission" under a NEW reference (`…-c01-r2`).
- **Frozen once sent**: the declaration, the clips and the original cannot change or be deleted once a clip
  is with Claru (the original is kept for the OneDrive backup, L5).
- **72-hour alert**: when Claru has not approved or rejected a clip 72 h after sealing, an alert opens, with a
  reminder every 6 h — one per interval — until Claru decides. In the app (Claru page, Recordings) and in
  the logs; no email in v1. "Seen" records that you know; reminders continue.
- **Claru page (admin)**: clips per state, overdue reviews, every call made to Claru (never the key or upload
  URLs). On the test server: test controls to make the mock approve, reject, refuse a seal, time out or
  rate-limit, so every outcome can be seen without the real Claru.
- **Mock Claru** now implements create / upload / complete / seal / poll from the guide, keeps its state across
  restarts, and refuses what it can see (wrong container, consent, size, duplicates, length).

Not in L4: OneDrive backup (L5), deleting files after delivery and backup (L6), the real Claru (L7).

Settings: `REVIEW_ALERT_HOURS` (72), `REVIEW_REMINDER_HOURS` (6), `CLARU_POLL_MINUTES` (3);
mock: `MOCK_CLARU_PROCESSING_SECONDS` (20), `MOCK_CLARU_AUTO_APPROVE_SECONDS` (0 = wait for you).

Gate:

- `npm run check` passes (delivery against the mock in-process: both upload shapes, a retried delivery that
  stays one submission, Retry-After obeyed, refusal → retry under the same ref, rejection → new ref,
  the alert schedule, permissions, no key in any log).
- On the test server: upload and declare → "In review at Claru"; approve one, reject one (Send again →
  "-r2"), refuse one (Claru page → Arm → Retry delivery). Set REVIEW_ALERT_HOURS=0.1 to see an alert in minutes.
